# SIN-246 — Tages-Update um 10:00 und 20:00

- **Links:** Linear [SIN-246](https://linear.app/sinan-kahraman/issue/SIN-246/tages-update-um-1000-und-2000-aufs-handy-gebaut-geplant-braucht-dich); [GitHub: `workflow_dispatch`](https://docs.github.com/en/actions/writing-workflows/choosing-when-your-workflow-runs/events-that-trigger-workflows#workflow_dispatch); [Telegram Bot API: sendMessage](https://core.telegram.org/bots/api#sendmessage); [cron-job.org](https://cron-job.org). Eine fertige Open-Source-Lösung gibt es dafür nicht, die Daten stammen aus unserem Loop (Linear, PRs, Content-Kennzahlen); darum Eigenbau auf den vorhandenen Funktionen von `status.mjs`, `linear.mjs` und `planner.mjs`.
- **Entscheidung:** `scripts/autonomy/digest.mjs` baut zweimal täglich (Slot `morgen`/`abend`) einen kurzen Kommentar mit @siinanXD im Issue „Loop-Status“. Der Workflow `digest.yml` läuft per `workflow_dispatch` (Eingaben `slot`, `dry_run`); cron-job.org löst ihn um 10:00 und 20:00 Europe/Berlin aus. Telegram kommt dazu, wenn `TELEGRAM_BOT_TOKEN` und `TELEGRAM_CHAT_ID` gesetzt sind. Dry-Run mit Fixture: `npm run autonomy:digest:dry`.
- **Annahmen:**
  1. Der Merker steht als HTML-Kommentar `<!-- digest: {day, slot, at} -->` im Kommentar selbst. Gibt es schon einen für Tag (Berlin) + Slot, sendet ein wiederholter Lauf nichts. `at` des letzten Merkers ist der Beginn von „seit dem letzten Update“; ohne Merker zählen die letzten 12 Stunden.
  2. „Klartext“ je PR kommt aus dem PR-Titel (Typ und Kennung entfernt, Bereich vorangestellt), kein KI-Aufruf: kostenlos und deterministisch. Die Spur folgt dem Scope des Titels (`content` → Content, `lernpfad`/`ui`/… → Frontend, `autonomie`/`ci`/Typ `chore`/`docs` → Infrastruktur, sonst Backend).
  3. Entscheidungen: neue Dateien `docs/decisions/SIN-*.md` aus der Git-Historie von `origin/main` seit dem letzten Update (Checkout mit `fetch-depth: 0`); ein Satz hinter „Entscheidung:“.
  4. „Braucht dich“: offene PRs mit `risk:high` ohne `freigegeben`, `needs-human` (PR und Linear), Linear-Issues mit `design` oder `abnahme`. „Fragen“ haben keinen eigenen Kanal und erscheinen als `needs-human`.
  5. Phase (SIN-244) ist im Repo noch nicht umgesetzt. Bis dahin gilt: alle Produktreife-Punkte grün → „beobachten“, sonst „bauen“. Sobald der Planer eine Phase kennt, wird sie hier übernommen.
  6. Kennzahlen zählen über 7 Tage (neue Einheiten, Kosten aus `docs/ops/content-runs`); Bestehensquote ist der nach Fragenzahl gewichtete Schnitt aller Module. Lässt sich etwas nicht lesen, steht „nicht verfügbar“, nie eine erfundene Zahl. Kontingente nur ab über 50 %.
  7. Der Kommentar kommt mit `github.token` (wie die Wächter-Meldungen); die Erwähnung löst den Push aus. Er löst keinen Workflow aus, das ist gewollt.
- **Nicht erfolgt:** Kein echter Lauf im Agent-Lauf (braucht Linear, GitHub und die cron-job.org-Jobs von Sinan). Das ist der Abnahme-Schritt nach dem Merge: `gh workflow run digest.yml -f slot=morgen`.
- **Warum:** Zwei feste Zeiten halten Sinan auf dem Laufenden, ohne dass er nachsehen muss; der Merker verhindert Doppelmeldungen, und alles Auswerten ist eine reine Funktion, die sich ohne Netz testen lässt.
