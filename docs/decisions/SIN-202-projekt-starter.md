# SIN-202 — Projekt-Starter: Plan zuerst, Ausführung erst nach stabiler Woche

- **Links:** Linear [SIN-202](https://linear.app/sinan-kahraman/issue/SIN-202/projekt-starter-neues-repo-mit-einem-schritt-infisical-vercel-sentry); [GitHub: Repo aus Vorlage](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-repository-from-a-template); [GitHub: wiederverwendbare Workflows](https://docs.github.com/en/actions/sharing-automations/reusing-workflows); [Supabase: Schemas über die Data API freigeben](https://supabase.com/docs/guides/api/using-custom-schemas); Vorgänger [SIN-310](SIN-310-sinan-issues.md), [SIN-306](SIN-306-figma-community-recherche.md), [SIN-309](SIN-309-deploy-schleife.md).
- **Entscheidung:**
  1. **Dieser PR liefert nur den trockenen Teil:** `scripts/autonomy/starter.mjs` (`plan`, `sql`) baut aus Name und Idee den Plan: Schritte je Dienst (GitHub, Infisical, Vercel, Sentry, Linear, Supabase, PostHog, Langfuse, cron-job.org, Leitstand, Figma), benötigte Konto-Tokens (nur Namen), Prüfung „schon erledigt“ je Schritt (wiederholbar), Start-Issues (AP-00, Design-Paket 1). Keine Netzaufrufe, keine Geheimnisse. `--live` bricht bewusst mit Hinweis ab.
  2. **Supabase-Standard „geteilt“:** ein Postgres-Schema je App im bestehenden Projekt, `schema_migrations` je Schema, RLS-Prüfabfrage; das SQL legt nur an, löscht nie. Modus „eigen“ prüft die Free-Grenze (2 aktive Projekte) und erzeugt bei Engpass eine `sinan`-Aufgabe statt Abbruch.
  3. **Konto-Tokens** liegen in Infisical `plattform/prod/konten` (Namen in `KONTO_TOKENS`); nur Loop-Workflows lesen sie, nie der Claude-Worker.
  4. **Eigenbau statt Fertiglösung:** Suche nach einer fertigen Lösung für „Repo + Infisical + Vercel + Sentry + Linear in einem Schritt“ ergab nur Einzel-Provider (Terraform-Provider, `gh repo create --template`). Sie decken Linear-Start-Issues und den Loop nicht ab; die Provider-Aufrufe werden später in den Schritten genutzt.
- **Annahmen:**
  1. **Nicht in diesem PR:** Workflow `new-project.yml`, Vorlagen-Repo, zentrales Plattform-Repo mit wiederverwendbaren Workflows. Ein Workflow mit Konto-Tokens bräuchte neue Secrets und wäre `risk:high`; außerdem gilt die Voraussetzung „eine Woche stabil“ (frühestens 12.10.2026). Das sind Folge-Issues nach dieser Woche.
  2. Live-Aufrufe gegen die Dienste konnten ohne Konto-Tokens nicht geprüft werden. Dienst-Grenzen (Supabase Free, PostHog, Sentry, Langfuse, Vercel Hobby nur nicht-kommerziell) sind aus der Issue-Vorgabe übernommen und werden vor dem Live-Schritt in den aktuellen Docs geprüft.
  3. Figma/FigJam-Grundausstattung (Datei, Pipeline-Ablauf, Nutzerwege) lässt sich per API nicht anlegen; sie steht im Plan als Aufgabe für Sinan.
  4. Freigabe von `PRODUCT.md` und „fertig“ je Projekt bleibt beim Menschen (`risk:high`).
- **Warum:** Der Plan ist testbar und legt Reihenfolge, Tokens und Prüfungen fest, ohne Konten anzufassen. So ist die spätere Ausführung nur noch Verdrahtung.
